# tree-sitter-texinfo

A tree-sitter grammar for GNU Texinfo. The reference for correct behaviour is
`texi2any` (Texinfo 7.3), whose command classes come from
`tta/data/command_data.txt` in the Texinfo sources. Where texi2any's error
recovery accepts what the Texinfo manual (`examples/texinfo-7.3/texinfo.texi`)
forbids, such as block commands in the middle of a line, follow the manual.
`TODO.md` tracks coverage.

The grammar is for structural editing and syntax highlighting, not for
producing documents. So the tree shows the source as written: conditionals,
macros and `@value` stay unexpanded, unlike in texi2any. It must also cope
well with incomplete input, which is normal while editing.

## Environment

- The Nix dev shell (`flake.nix`) provides tree-sitter, Node, clang/clangd,
  texinfo and Python with py-tree-sitter. direnv loads it automatically; after
  changing `flake.nix`, run commands through `direnv exec .` until the session
  restarts.
- GNU coreutils and sed are on the path, not the macOS ones: use `sed -i`, not
  `sed -i ''`.
- `examples/` is a symlink, created by the dev shell, to real manuals
  (extracted by `script/extract-examples.py`) pinned by
  the `reference` input in `flake.nix`, with texi2any itself and apart from
  the tools: texinfo, make, sed, gawk, glibc, gdb, binutils, bash,
  coreutils, autoconf, automake and Emacs's manuals, and by other authors
  SBCL's (`.texinfo` files, ASDF's among them), Maxima's (in English and
  Japanese), GNU Parallel's (made by pod2texi), Stow's and the LaTeX2e
  reference manual: about 690 files. Some are chapters of a manual, in
  separate files. Texinfo files are `.texi`, `.texinfo` or `.txi`; the checks
  take all three. It is not committed.
- The scripts that check many files take them all in one run (the flags
  under Checks, or standard input), never through `xargs`: it splits a long
  list over several runs, and a check that compares the whole set (a
  snapshot of a file no longer checked, the median speed) goes wrong.
- tree-sitter CLI: `tree-sitter parse` only finds the grammar when run from
  the repository; `-d FILE` takes FILE as the debug level (use
  `--debug=normal`); `tree-sitter fuzz --include` matches names like
  `texinfo - corpus - FILE - NAME`, so `^` never matches. `tree-sitter test`
  or `parse` in a scratch copy of the repository builds its parser into the
  same cache (`~/.cache/tree-sitter/lib/texinfo.dylib`), which the
  repository's then uses until its own `src/` changes: pass `--rebuild`
  after one.
- `texinfo-tests/` is a symlink to the inputs of texi2any's own parser tests,
  one file per test case (about 1,750), extracted by
  `script/extract-texi2any-tests.pl`. Many are deliberately invalid, so parse
  errors there are expected; it is not committed either.

## Layout

- `grammar.js`: the grammar. Sections by level (`SECTIONS`, mirrored by
  `SECTIONING` in the scanner) and the commands whose arguments split at
  commas into named fields (`ARGUMENT_COMMANDS`) are listed here.
- `src/scanner.c`: external scanner. Holds the tables of line commands
  (`LINE_COMMANDS`, and `PARAGRAPH_ENDING_LINE_COMMANDS` for those that end
  a paragraph, as texi2any's close_paragraph_commands; the others may be
  inside one) and built-in brace commands (`BRACE_COMMANDS`, from
  texi2any's command table), and the table of block names and kinds
  (block, list, multitable, float, raw, macro (a `macro_definition`), menu,
  definition with its layout, whose numbers
  index `DEFINITION_LAYOUTS` in `grammar.js`), the stack of open blocks that makes `@end NAME`
  match, raw block bodies, `@verb` bodies (its delimiter is saved state), the
  zero-width `missing_brace` and `missing_end` tokens that close unclosed
  brace commands and blocks, `unmatched_end` for an `@end` that ends no open
  block, the `@node` tokens that look ahead to the
  section a node line starts, the zero-width glue between the parts of a
  definition line's word, the names of the commands that start no
  paragraph (`NO_PARAGRAPH_COMMANDS`) where one would start and of raw
  blocks at a paragraph's next line, which don't end it, a zero-width end
  of a paragraph before a brace command that ends one in the middle of a
  line (`PARAGRAPH_ENDING_BRACE_COMMANDS`), a zero-width token before
  `@image` and `@namedanchor` where they start no paragraph, conditionals
  of text inside a paragraph (it reads the conditional's first line), the
  rest of the `@end` line of a block in a paragraph, and the end-of-file
  token. Add new blocks here.
  Its token enum lists the grammar's `externals` in order, under the same
  names, and its tables of definition layouts and section levels mirror
  the grammar's; `script/check-scanner.py` checks that they agree and that
  its tables of names don't overlap.
- `src/` (except `scanner.c`) is generated by `tree-sitter generate` and is
  committed; always commit it together with the `grammar.js` change.
- `test/corpus/*.txt`: corpus tests.
- `script/compare-texi2any.py`: compares our trees with texi2any's.
- `queries/`: highlights, injections, folds, tags and textobjects, editor
  neutral: where editors' capture names differ, the plainer one (README).
  `.tsqueryrc.json` lists the names it uses, so `ts_query_ls` rejects any
  other; add a new one there only after checking every editor has it, or
  map it in the generator. No indents, as Texinfo isn't indented by nesting.
  `script/editor-queries.py` generates `editors/helix/queries/` and
  `editors/neovim/queries/` from them, renaming captures by a table per
  editor (a pre-commit hook fails if they're stale), each checked against
  the editor's own names in `editors/NAME/tsqueryrc.json`. Those lists come
  from Helix's book (`themes.md`, the textobject and injection guides) and
  from nvim-treesitter's and nvim-treesitter-textobjects' `.tsqueryrc.json`;
  refresh them when an editor adds names. To support another editor, add its
  table and list. Edit only `queries/`. `tree-sitter query queries/textobjects.scm FILE` shows what a
  textobject captures; highlight and tags
  tests are in `test/highlight/` and `test/tags/` (run by `tree-sitter
  test`); those of folds, textobjects and injections in
  `test/queries/QUERY/`, run by `script/test-queries.py` (in the `tests`
  check), as tree-sitter 0.26.11 reads a test in `test/QUERY/` as the
  query itself: the same assertions, which it fails, rather than skips,
  where they aren't comments, and `N lines up` for a raw block's body. `ts_query_ls format queries/` formats them; `ts_query_ls check`
  validates them against the grammar (built with `tree-sitter build`). Tags
  queries only allow tag captures, so their predicates test the
  text of the whole captured command. An assertion in a highlight or tags test is only
  checked where `@c` is a comment: not after `@bye` or inside a raw block,
  where it is silently skipped. Check the assertion count `tree-sitter test`
  reports.

## Checks

A Claude Code hook (`.claude/hooks/check-grammar.py`) runs `tree-sitter
generate` and `tree-sitter test` after every edit to `grammar.js`,
`src/scanner.c` or the corpus made with the Write or Edit tools (not one
made through Bash, after which run them yourself). Every other check is declared in `flake.nix`
(with flake-parts, and treefmt-nix's and git-hooks.nix's modules) and run
by `nix flake check` (`just check`), locally as in CI. Nix caches them: a
check whose inputs didn't change isn't rerun, and each check's inputs are
only the files it reads (`mkCheck`'s list), so a change to the docs, a
query or the snapshots reruns only the checks that read them (`pre-commit`
reads every file); CI keeps the store between runs too. Each check's
command is a shell application, which shellcheck checks; its fuzzing starts
from a fixed seed, so that its result depends only on its inputs. Run it before pushing, so CI only confirms. One check by
name: `just run NAME`, with NAME one of `pre-commit` (formatting and the
linters), `generated`, `tests`, `scanner-warnings`, `scanner-tables`,
`parser-size`, `fuzz`, `checks-catch`, `parse`, `compare-manuals`,
`compare-tests`, `snapshots`, `fuzz-inputs`, `edits`, `neovim-queries`,
`fuzz-scanner`.
`nix fmt` (`just fmt`) formats every file. The justfile only holds such
one-line aliases; `just` lists them.

The Python scripts select their own files: `--manuals`, `--edited-manuals`
(without gawk's Italian ones), `--compared-manuals` (also without the files
texi2any fails on), `--test-inputs`, `--corpus-inputs` (each corpus test's
input, written to `build/corpus/FILE/TITLE.texi`), or names given as arguments or on
standard input; from the repository's root, which they check, as the names
they record are relative to it.

`script/tree-snapshots.py` checks every manual's and test input's tree
against `test/tree-snapshots.txt`, digests of the full trees. After a
deliberate change to the trees, review it with `just snapshots-diff HEAD
FILE...` on the files it names, then record it with `just snapshots-write`. `script/check-edits.py`
simulates typing mistakes in the manuals' paragraphs: each must leave the
tree outside its paragraph unchanged (as texi2any's error recovery does), and
an incrementally parsed tree must equal a fresh parse. The check runs it
with `--seed 0`; other seeds find other edits (`just edits 3`), so try a few
after changing the scanner or error recovery. Its docstring says which edits are expected to
reach further, as in texi2any; add to them only with a reason, as to the
lists of differences. `--keep DIR` saves the edited text of each problem, to inspect with
`tree-sitter parse --cst` or `--debug-graph` (`tree-sitter parse --edits`
rejects every edit in tree-sitter 0.26.11). `script/parse-examples.py` checks
that only the manuals in `test/parse-errors.txt`, each with its reason, fail
to parse, and that none parses ten times slower than the median; with
`--stress` (as the check runs it), also generated inputs no manual has,
such as a line of thousands of commands.
`script/fuzz-corpus.py` turns texi2any's test inputs and the manuals into a
corpus file that git ignores, for `tree-sitter fuzz --include texinfo-tests`
or `--include examples` (about 10 seconds an iteration for the manuals);
delete it afterwards (`script/fuzz-deep.py` does), or `tree-sitter test`
runs it too. It
writes the expected trees itself: `tree-sitter test --update` would drop the
delimiters' suffix, after which a line of dashes in a manual ends its input.
`script/test-checks.py` runs these checks on small inputs in `test/checks/`
whose outcome is known, and fails if one no longer reports what it should
(or reports something it shouldn't); add a case there when a check gains a
way to fail.

The git hooks are pre-commit's, declared in `flake.nix` with git-hooks.nix
and installed by the dev shell (which writes `.pre-commit-config.yaml`, git
ignores it): on commit, treefmt (the formatters of `nix fmt`), ruff,
ESLint (as `package-lock.json` pins it, built by Nix), shellcheck,
actionlint, the queries' capture names, and that each editor's generated
queries are up to date; on the commit
message, convco (Conventional Commits); before pushing, that `src/` matches
`grammar.js` and `tree-sitter test`. `pre-commit run --all-files` runs them
by hand (the pre-push ones with `--hook-stage pre-push`); `nix flake check`
runs the commit ones as its `pre-commit` check, and the others as its
`generated` and `tests` checks.

The `fuzz-scanner` check runs libFuzzer with sanitizers on the parser and
scanner for 60,000 runs from a fixed seed, about two minutes (harness
`test/fuzz/harness.c`; the scanner built with `test/fuzz/checked_scanner.c`,
which aborts on what no tree shows, such as a newline left in a token's
padding; dictionary from `script/fuzz-dict.py`, seeds from
`script/corpus-inputs.py`); `just
fuzz-scanner [SECONDS] [JOBS]` runs it longer and on several cores, keeping
what it covers in `build/fuzz/out`. LLVM is version 23, not nixpkgs' default
21, whose AddressSanitizer deadlocks at startup on macOS 27. `just fuzz-deep`
(`script/fuzz-deep.py`) runs `tree-sitter fuzz` on texi2any's test inputs
and the manuals for longer than the checks, on several cores. The checks run
it through `script/fuzz.py`, which fails on a test it reports failed:
`tree-sitter fuzz` exits with 0 whatever it finds.

CI (`.github/workflows/ci.yml`) runs `nix flake check` on every push, except
one that only changes Markdown files; a newer push cancels a run in
progress. It also builds and tests the bindings on
Linux, macOS and Windows (where MSVC compiles the scanner). The
comparisons pass only if the differences from texi2any are exactly those
listed in `test/texi2any-differences.txt`, each file with a `#` comment giving
the reason: deliberate (the Texinfo manual over texi2any's error recovery,
source kept unexpanded), invalid input (with texi2any's own error), a limit of
the comparison, or a gap still to fix (also in `TODO.md`). A difference not
listed fails, and so does a listed one no longer found. After a deliberate
change, or a fix, run `just compare-write`, check the diff of
`test/texi2any-differences.txt`, and give each new file a reason; never list
a regression. To compare by hand: `python3 script/compare-texi2any.py
--compared-manuals` or `--test-inputs` (a minute or two each).

The comparisons skip the files texi2any itself fails on (the Italian gawk
manuals, `texinfo-tex-test.texi`) and `html_default_commands_args.texi`, a
fragment for `@include`. The script doesn't imitate what texi2any expands
(macros, `@value`, aliases, conditionals): our side parses texi2any's own
expansion of the file (`--macro-expand`), after checking that texi2any finds
the same document in it; for invalid input it often doesn't, and the script's
docstring says what it does then. Use `--structure` to compare only blocks,
items, line commands and menu entries.

`nix flake update` moves the tools but not the `reference` input, a fixed
nixpkgs revision for texi2any and the manuals: a new texi2any or manual
changes many listed differences and snapshots at once. Move it in a commit of
its own, changing only the revision in `flake.nix`: run `just compare-write`
and give each changed difference its reason, review the trees with `just
snapshots-diff`, then `just snapshots-write`; a manual's new version is a new
path, so its old snapshots go and new ones come.

The comparison checks which commands appear, in order (a menu entry is
`*`, and a block's end counts where it ends without its `@end` too), then
the arguments of each command found on both sides: field by field
where the grammar splits them as texi2any does (at commas, a definition line
into its words, a menu entry into its parts; the positions are the grammar's
`ARGUMENT_COMMANDS` and the script's tables), as one otherwise. Then where
paragraphs start and end among the commands (`<p>` and `</p>`), and in
preformatted blocks and menus, where texi2any has none, the stretches of
preformatted text it has instead (`<pre>`), and the text of each outside
its commands. Only an
argument's letters and digits count (of any script), without spaces, with the
names of the commands in it but not its comments, so a difference in spaces
or punctuation alone, in a field's node type or in how sections nest shows
up only in corpus tests and the snapshots. A difference in
arguments is listed as `line N: @xref arguments: ours 'a | b', texi2any
'a b'`, the fields separated by `|`, one in paragraphs as `line N:
paragraphs: ours '</p>', texi2any '(nothing)'`. To
find scanner code no corpus test reaches, build a small harness with
`-fprofile-instr-generate -fcoverage-mapping` and read it with `llvm-cov`
from the same LLVM version as the compiler (the profile format differs).

## Conventions

- Commit messages follow Conventional Commits (`feat:`, `fix:`, `test:`,
  `build:`, `ci:`, `refactor:`, `docs:`, `chore:`).
- Test first: for new behaviour, write the corpus test with its expected tree
  by hand, based on what texi2any does, and see it fail before changing the
  grammar. The `compare-tests` check compares the corpus inputs with
  texi2any too, so one that differs on purpose is listed with its reason
  (`just compare-write`). Use `tree-sitter test --update` only to regenerate existing tests
  after a deliberate change to the tree's shape, and read every regenerated
  tree before keeping it.
- A corpus test's input starts right after the header line, so a blank line
  there is part of the input.
- Mark tests that must produce a parse error with `:error` under the title.
- Keep line-start rules in the grammar (every line-level rule ends in
  `_line_end`), not column checks in the scanner. tree-sitter (since 0.19.5)
  re-lexes an external token whose scan called `get_column` when an edit
  moves it along its line, but before 0.27.1 (October 2026; editors bundle
  older runtimes) it doesn't record the call in a scan that returns false:
  the token the internal lexer reads instead is reused after an edit that
  would make the scan succeed. So a column check may only choose between
  the scanner's own tokens, or apply where an edit that changes its outcome
  touches the token. The scanner checks only column 0, where nothing comes
  before a token on its line, to close a brace and end a paragraph after a
  line command inside the braces took the newline, and only where the
  answer decides the token: `get_column` counts from the start of the line
  on every call, so asking before each token made a long line's parse
  quadratic. `script/check-edits.py` checks that incremental parsing still
  matches a fresh parse.
- Update `TODO.md` in the same commit as the work it tracks.
- Neovim reads `#match?` regexes as Vim's "very magic" ones, where `@` is
  an operator: write `[@]`, or use `#any-of?`. The `neovim-queries` check
  runs the generated Neovim queries in Neovim.
- In `highlights.scm`, editors resolve overlapping patterns differently:
  the tree-sitter CLI (and so the highlight tests) keeps the match that
  finishes first, dropping every other match that captures that node with
  all its other captures, and the rest of a match after a private capture
  like `@_name`; Neovim and Helix let the last pattern in the file win. So
  keep patterns from overlapping (use predicates to make them exclusive)
  and capture predicate nodes with a real highlight.
- Recognise long lists of command names in the scanner, not with keywords in
  the grammar: every keyword is an entry in every parser state where a
  command can start. Moving 199 keywords to the scanner took `parser.c` from
  29 MB to 6 MB (it is 14 MB now, with 7,100 states).
  That is the table's size: a few keywords in place of one cost no states.
- Watch `tree-sitter generate` time (normally about a second) and the
  parser's state count, which has a budget: the `parser-size` check
  (`script/parser-size.py`) fails above it, and more than 10% under it.
  Raise `BUDGET` only with the change that needs it, after measuring why it
  costs what it does; each feature's few percent went unnoticed, until the
  parser had twice the states. Optional parts that may be left out
  anywhere, as a command's comma-separated arguments may be empty, expand
  into a production for each combination of those present, and the parser
  into states for each: write them as a chain of hidden rules, one for each
  position, holding the next (`commaArguments`, and a definition line's
  words): 13,748 states became 7,139, with the same trees, and generation
  went from ten seconds to one. A change in nested optional sequences once
  made generation run for over 13 minutes. `tree-sitter generate
  --report-states-for-rule -` counts the states that each rule's items are
  in, which shows where they go.
- Measure a grammar change's cost before implementing it: generate in a
  scratch copy and read `STATE_COUNT` in `src/parser.c`. An alternative in a
  rule used in many contexts often costs far less as a hidden rule of its own
  (macro parameters: 979 → 166 states), or allowed only where it occurs. A
  rule has states of its own for each set of tokens that may follow it, so
  let the same ones follow it everywhere where that's harmless (a
  `line_argument` after `@alias` that no `@subentry` could follow: 384
  states). An alias of a rule listed in `inline` doesn't make a node.
- Keep the scanner's state to what nests (the stack of open blocks) or lasts
  a token or two (the `@verb` delimiter): no tables of names the file
  defines (macros, `@set` variables, aliases). The scanner once remembered
  the file's macros, to parse their calls as texi2any does: every token
  after a definition then carried the table in its state, so adding or
  renaming a macro reparsed the rest of the file, state over 24 bytes cost
  a heap copy per token, and macros defined in another file (`@include`)
  were unknown anyway.
- Token precedence doesn't stop a longer match by another token valid in the
  same state; make the grammar allow only one of them there instead. And a
  token with precedence is lexed wherever it is valid as the lookahead of a
  reduction, even where the state the reduction leads to has no use for it:
  a menu entry's `*` made a `* ` line in a definition's body an error, until
  the scanner gave an entry's start only in a menu.
- The scanner may choose a token by which others are valid, but the choice
  must be the same before a reduction and after it: a fresh parse lexes the
  token after a node before reducing it, and an incremental one that reuses
  the node lexes it in the state after. Nor may a node hold only what the
  tokens after it decide: tree-sitter reuses a node built without a
  conflict even where the next tokens changed. Such a hidden rule goes in
  `inline` (`_paragraph_line_commands`, after which no more line commands
  could follow, and `_body_start`, a newline that an `@deffnx` after it
  makes part of the head); `tree-sitter fuzz` finds what breaks this.
- Favour error recovery that keeps the rest of the document intact: a
  mistake being typed should only affect its own paragraph or block, as in
  texi2any. tree-sitter's own recovery often doesn't manage that, so close
  constructs explicitly where texi2any does (see `missing_brace`).
